# リリースノートの作成・確認手順

本書は今後のリリース作業で、人・AIの双方が必ず参照する。リリースの実施は別途明示的な指示を必要とする。

## 取得元と共通方針

Web GUIはGitHub REST APIの `releases/latest` から取得したRelease本文 `body` を表示する。ローカルの過去版MarkdownはGUIの取得元ではない。本文をGUI用とGitHub用に分けず、同じユーザー向けの変更案内を使う。
[GitHub公式API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)を参照。

リリースノートは「ユーザーにとって何が変わったか」だけを簡潔な自然な日本語で書く。
機能追加、改善、不具合修正、操作・利用方法への影響、互換性、必要な設定変更、既知の制限を対象とする。
実装済みの変更だけを記載し、確認できていない効果を断定しない。「安定性を改善」など曖昧な表現だけで済ませず、具体的な利用者の変化を書く。

テスト詳細・件数・成否、検証したファイル・関数・モジュール、内部構造、リファクタリング詳細、CI/CD結果、調査過程、開発作業報告、コミットID、内部管理情報、ユーザーに影響しない内部変更は記載しない。
検証記録は別の開発者向け記録に保存し、Release本文へ貼り付けない。

## 必須フロー

1. 差分から利用者への影響を抽出し、下のテンプレートに必要な項目だけ記載する。空の項目は削除する。
2. テスト・調査・内部実装の記録を別ファイルで作成する。ノート生成スクリプト・Release自動作成workflowは現在存在しない。コミット一覧やGitHubの自動生成ノートをそのまま公開しない。
3. `python packaging/check_release_notes.py <本文ファイル>` を実行する。検査に失敗した本文は使用しない。検査は代表的な内部情報の混入検出であり、文章の意味・事実の一致は人が確認する。
4. 人・AIとも差分と本文を照合し、実施していない改善、未確認の効果、開発報告が含まれないことを確認する。
5. 別途リリース実施を指示された時だけ、検査した同一ファイルをGitHub Releasesの本文として使用する（CLIなら `--notes-file`）。自動生成ノートの追加はしない。公開前にGUIでも読める文章として最終確認する。
6. 公開後、GUIの更新確認で同じ本文を取得・表示できることを確認する。既存公開済みReleaseの編集は別途指示がある場合のみ行う。

将来、AI指示書・テンプレート・生成処理・公開workflowを追加する場合にも本書と本文検査を必須にする。検査なしの公開経路を作らない。

## テンプレート（実際の本文ではない）

```markdown
## 追加・改善
- 利用者にとって変わる機能・操作を具体的に記載。

## 修正
- 発生条件と、修正後の動作を簡潔に記載。

## 利用上の注意
- 必要な設定変更・互換性への影響・既知の制限を記載。
```

不適切：保存処理の関数を分割し、12件のテストが成功しました。
適切：一時的な保存遅延の案内を点検・診断画面にまとめました。
これらは記述例であり、リリース済みの変更を示すものではない。

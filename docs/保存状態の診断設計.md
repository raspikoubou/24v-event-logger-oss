# 保存状態の診断設計

## 現行処理と限界

実daemonはBackgroundEventWriterの専用スレッドでSQLiteへ保存する。GPIO変化の安定確認後、Clockから取得したUTC・monotonic時刻を不変eventとしてキューへ投入し、最大32件をFIFOでtransaction保存する。SQLite保存の完了時刻でevent時刻を書き換えない。同期EventWriterは注入テスト用であり、実daemon経路とは異なる。

保存待ち中も入力検知・確定処理は継続できる。ただしOS負荷・GPIO callbackの遅れ・ロック競合による検知精度の影響まで保証するものではない。commit遅延と入力検知遅延は別である。

キューはcommit処理中を含め最大10,000件のRAM保持。満杯では投入を拒否しCriticalへ遷移するため、当該eventを保持できない。保存失敗時はtransactionをrollbackしてbatchを先頭へ戻し、workerを停止、daemonへ失敗を伝えCriticalにする。自動再試行・永続スプールはない。電源断・プロセス終了では未保存eventを失い得る。欠損を網羅的に検出する機構はなく、遅延履歴があるだけで欠損と判定せず、欠損がないとも断定しない。Critical・通信不能の既存通知は維持する。

## 計測と判定

commitの開始からappend_many完了までをmonotonicで計測。500ms以上の完了commitの回数・最大値を直近5分で保持する。500msは従来の診断用閾値であり、欠損・故障の境界を示す実測根拠はない。最古の未保存eventの滞留は投入からcommit完了まで（処理中も含む）。進行中commit・最後のcommit・未保存件数も保持する。

| 重要度 | 発生条件 | 表示 |
|---|---|---|
| 正常 | 以下に該当しない | 警告なし、診断値は維持 |
| 注意 | 直近5分に500ms以上の完了commitが1回以上、または現在のcommit/滞留が500ms以上 | 点検・診断のタイトル上の注意欄のみ |
| 警告 | 現在のcommitまたは最古滞留が5秒以上、未保存件数が容量80%以上、worker保存失敗 | 全画面のタイトル上の共通注意欄（詳細は点検・診断で表示） |

5秒は既存の正常負荷での最大保存追従目標を超える境界を維持する。80%は固定event頻度ではなく有限容量の危険度であり、残り20%を回復余地として確保する保守的な閾値。特定入力速度での残り時間や実機での最適値を保証しない。

警告解除：保存失敗なし、commitと最古滞留がともに1秒未満、使用量が50%未満を、診断サンプルで10秒間維持する。再び悪化すると回復タイマーをリセットする。時刻はmonotonicを使う。注意は5分の履歴が期限切れし現在の遅延も500ms未満になれば解除。worker失敗は同一workerで解除せず、原因解消と再起動を必要とする。

完了commitが繰り返し遅くても、未保存滞留・容量・失敗の警告条件に達しない場合は注意。commit回数だけで重大な記録障害としない。判定はstatus取得時に更新するため、取得間隔未満の状態変化の監視には限界がある。
